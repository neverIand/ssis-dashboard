# Read-only API contract

Updated: 16 October 2026. Milestones: C1a–C7b implemented, C8.1 combined acceptance, C8.2a measured NULL binding and C8.2b.1's [current-catalog workload baseline](API_WORKLOAD.md) complete locally. **All 14 Stage C GET operations, including bounded exact-package history and prior-success estimates, are implemented.** C8.2b.2/.3 larger workload/fix/budget acceptance, C8.2c resources and C8.3 independent reader HTTP remain required. [OpenAPI](openapi.yaml) defines fields, parameters, examples and response schemas; this document defines cross-field rules and local access policy. The [acceptance matrix](API_ACCEPTANCE.md) records deliberate legacy differences, combined native checks and remaining gates. Track delivery in [PROGRESS](PROGRESS.md#stage-c--read-only-api-delivery-phase-2). The [roadmap](roadmap.md) governs scope.

## Delivery and compatibility

Stage C covers 12 `/api/v1` resources plus `/healthz` and `/readyz`. OpenAPI marks all fourteen operations `implemented` and records their delivery milestones; C7b implements history's separate estimate fields. An implemented operation does not complete its remaining feature/integration gates. The stream contract belongs to phase 5 and is deliberately absent from the Stage C paths; the existing SSE requirement remains in the modernization plan. `/meta` and the execution sort parameter expose the same 12 implemented sort keys; unknown keys still return 400.

Keep legacy routes, formatted SQL results and HTML errors working through their adapter. The API has its own typed result models and safe JSON errors. Use `GET` for monitoring; ordinary `HEAD` has the same policy/status/headers and no body, and Flask may answer `OPTIONS` with method information. Neither provides a capability bypass. Other methods return 405 with `Allow`. GET requests have no request body. Frontend and API share an application origin and base path; the spec's `/` server denotes the local root binding, and a later prefix deployment must publish the correct base URL. Do not hardcode the origin root in clients.

The draft version is `1.0.0-draft.1`, independent of the legacy app version. Fields and examples describe the target, not live responses. Consumers tolerate added response fields; removing/renaming fields or changing their meaning requires a versioned contract decision. Input parameters remain strict to detect misspellings.

## Local access policy

The initial API is for a loopback-bound process under one configured SQL identity. Loopback binding is a launcher/deployment requirement; an HTTP Host header, forwarded header or claimed user name cannot establish that boundary. This milestone adds no login system, proxy trust or public/shared exposure.

All catalog queries enforce the configured SQL connection identity's visibility. A browser does not choose a database identity. Cursors, IDs and filter names grant no access. Do not introduce a cross-user result cache, wildcard CORS or trust in browser-supplied identity/proxy headers. Shared authentication/delegation and production transport remain B5c work; the OpenAPI `security: []` describes this local mode and must not be read as approval for anonymous shared hosting.

These application settings are implemented and validated at startup in C1c. API capability guards run before view/SQL work, including for HEAD and automatic OPTIONS. The flags govern API routes; legacy pages retain their existing SQL-identity access during coexistence. C5 implements events; C6 implements both values sections and their independent redaction serializers:

| Setting | Default | Effect |
| --- | --- | --- |
| `API_EVENTS_ENABLED` | `False` | Event text and search endpoint returns safe 403 before any execution/event query until deliberately enabled for this SQL reader scope. Aggregate counts remain available. |
| `API_VALUES_ENABLED` | `False` | Both sections of the values endpoint return safe 403 before any execution/value query until deliberately enabled. Enabling permits nonsensitive parameter values and override metadata. |
| `API_OVERRIDE_VALUES_ENABLED` | `False` | With values enabled, override values remain NULL with a policy redaction marker. Enabling deliberately permits nonsensitive override values in this SQL reader scope; it cannot override a catalog sensitive flag or unmask a catalog NULL. |

Require actual booleans and reject contradictory configuration (`API_OVERRIDE_VALUES_ENABLED=True` while values are disabled). `/meta` returns effective capability booleans, not identities, connection strings, host names or secret configuration. Basic execution metadata, recorded event counts and timing statistics need no text/value capability. If a capability is denied, 403 is independent of whether an execution exists. For allowed execution-scoped resources, look up visibility first: absent and hidden executions have the same safe 404 and no follow-up query. A visible execution with no child/event/value rows returns an empty collection; SQL errors remain errors.

The serializer always forces a sensitive parameter or sensitive override's `value` to NULL and `redacted` to true, even if a faulty row adapter supplies plaintext. Preserve `redaction_reason: sensitive` versus `policy`; SQL NULL without redaction is `value: null, redacted: false, redaction_reason: null`. Never decrypt catalog data. Enabling free-text events or nonsensitive values authorizes their exposure for this reader scope; their contents can still include operational secrets and cannot be automatically declared safe from a flag alone.

Every API/health response, including errors, uses `Cache-Control: no-store` and a server-generated `X-Request-ID`. Application logs exclude values, messages, raw URLs/query strings, cursors, search text, SQL and diagnostic exception text. The existing safe timing/error event boundary remains. Host/access/proxy/startup logs are a separate deferred check; application redaction does not close it.

## Query parsing, names and filters

Reject unknown keys, repeated keys, empty values, unsupported enum tokens, malformed UTF-8/percent encoding, NUL and malformed IDs before catalog acquisition. Integer query inputs use ASCII decimal digits, without signs, whitespace, exponent or fractional notation; IDs also reject leading zeroes. Do not turn an invalid supplied integer into its default. Parse URL encoding once; never unquote again. No trimming or case folding of names. `folder`, `project` and `package` are exact catalog equality predicates; case/accent equivalence follows the catalog collation. Literal `all`, `*`, `%`, `_`, `[`, `#`, slash, backslash, plus and Unicode names have no sentinel meaning. A literal plus must be encoded as `%2B`; clients should use `URLSearchParams` or equivalent.

Catalog folder/project/environment names allow up to 128 UTF-16 code units; package names allow 260. OpenAPI `maxLength` is a Unicode character upper bound; additionally enforce the SQL UTF-16 width before binding. Use matching SQL parameter widths instead of the legacy 100-character declarations.

The execution list and metrics accept separate `folder_pattern` and `project_pattern` fields (maximum 512 UTF-16 units). An exact and a pattern field for the same name are mutually exclusive. Only `*` means zero or more characters; `\*` means a literal asterisk and `\\` a literal backslash. Reject other/dangling escapes. Escape SQL `%`, `_`, `[`, and the chosen SQL escape character; bind the translated pattern with enough width for the escaped result rather than truncating it to the catalog name width. The API never accepts a raw SQL LIKE fragment. `/projects` requires an exact folder; history requires exact folder/project/package. The execution list may span folders/projects when selectors are absent.

C3a navigation describes the current visible catalog independently of execution time/status filters. `/folders` includes only visible folders containing at least one visible project. `/projects?folder=...` requires a nonempty exact folder name and returns actual project/parent IDs with unique field aliases. Unknown, hidden or empty folder scopes return an empty collection, with NULL `upper_id` on the first page. Both resources accept only their declared navigation inputs; time, status and pattern selectors are rejected. Descriptions preserve NULL versus empty text and allow at most 1024 SQL UTF-16 units; no HTML interpretation or trimming occurs.

Optional `status=2,7` is a comma-separated set of known codes 1–9 (no spaces, duplicates, empty entries, `0` or `all`). Omission means all execution statuses, including future unknown codes returned by the catalog. Unknown numeric output codes retain their number with name `unknown`; they do not crash serialization. Execution status and summary codes retain the full signed SQL INT range (-2,147,483,648 through 2,147,483,647). Execution result codes use a separate vocabulary. Reject unsupported input codes until a later contract explicitly permits them.

## Time, cohort and representation

Accept `from` and `to` only as offset-aware RFC 3339 timestamps, including `Z`, with at most seven fractional digits and offsets no greater than 14 hours. Require uppercase `T`/`Z`; reject offset-free values, the unknown `-00:00` offset and leap seconds. Output UTC timestamps ending in `Z`, preserving up to seven fractional digits, including the seventh SQL digit when present. Do not pass timestamps through a timezone-less SQL cast or local display formatting. [C1b's native proof](PROGRESS.md#c1b--exact-typed-sql-to-json-boundary) validates the opt-in connection-local converter and exact SQL parameter binding on the recorded Windows/Driver 17 baseline; endpoints must use this boundary. Canonical output emits seven fractional digits.

Use the half-open execution cohort `created_time >= from AND created_time < to`. Resolve omitted `to` once from the request clock, or from a configured fixed `AS_OF_DATE`; omitted `from` is `to - HOUR_SPAN` hours (default 360). This is elapsed time, not a count of civil days. Require `from < to` and a default maximum span of 744 hours (31 elapsed days); proposed `API_MAX_RANGE_HOURS` is a positive administrator override. The effective default range must fit the cap. A fixed legacy `AS_OF_DATE` accepts an ISO date (local midnight) or date-time; without an offset it is interpreted in the configured display timezone only if it identifies one valid instant; ambiguous/nonexistent local times are configuration errors and require an explicit offset. A historical upper bound limits creation time; statuses and event counts still reflect observations now.

The execution list, summary and timeline return effective UTC `meta.from`/`meta.to`. Reuse these exact values across requests so a new clock resolution cannot produce different cohorts. List/timeline use the selected status; summary accepts and validates that selection for shared filter URLs but intentionally counts **all** statuses and reports `status_scope: all`. Include zero entries for known status codes and separate entries for any observed unknown code; `total` includes both. These are current status observations, not a cross-request snapshot.

C3b summary shares cohort parsing with the execution list and aggregates the matching public catalog rows once, without event/logging joins. It accepts no paging/sort/cursor inputs. Return status entries in numeric-code order, with nine known zero entries for an empty cohort. Limit the combined known/unknown entries to 65,536; SQL fetches at most 65,537 grouped rows to detect overflow. Duplicate/unexpected groups, oversized counts or a total beyond JavaScript's exact integer range fail safely with 500 rather than returning partial or rounded totals. This bounds results, not the whole-cohort aggregation cost. Native work/reader evidence and the measured cached-plan decision are recorded in PROGRESS.

The display timezone is configured by `DISPLAY_TIMEZONE`, default `Europe/London`, and exposed by `/meta`. Application construction validates that the IANA identifier is loadable; the pinned first-party `tzdata` runtime dependency supplies data on Windows and other hosts without a system database. Legacy display formatting is unchanged. C3c day/hour timeline buckets follow that configured timezone and return unique UTC start/end instants. DST days need not contain 24 hours; repeated local hours remain separate buckets with different UTC bounds. Include zero buckets intersecting `[from,to)`; edge buckets may extend beyond the range but count only executions within it. `API_MAX_TIMELINE_BUCKETS=1000` may be lowered to a positive value but cannot exceed the 1000-bucket wire limit. Count actual intersecting buckets, including partial edges; exceeding the cap returns 400 without silently widening bucket size.

Timeline defaults to `bucket=day`. A calendar day starts at its first real local midnight, or the transition instant when midnight is skipped. Repeated midnight belongs to one longer day; a wholly skipped date creates no empty fictional day. Hours use valid local hour starts plus offset transitions, so a non-hour DST change can create a shorter partial hour. Intervals are ordered and contiguous in UTC. Requests whose complete bucket edges cannot fit the supported year 0001–9999 UTC range return 400 before SQL. The application generates exact UTC intervals from IANA data; the database does not reinterpret the display timezone.

Timeline applies the selected statuses before aggregation. Empty `meta.selected_statuses: []` means all statuses, including unknown output codes. `created_count` counts matching executions created in the bucket; `started_count` is the subset with a non-NULL actual start, even when it started later. `succeeded_count` and `failed_count` use current status 7 and 4, respectively. None is grouped by start/end date or reconstructed at a historical `to`. An empty visible cohort returns every intersecting bucket with four zero counts. Summary and timeline can share exact effective bounds, but summary intentionally ignores selected statuses.

All IDs/LSNs are decimal strings within SQL BIGINT range; execution IDs are positive, and `0` is never an aggregate selector. Do not use floating-point IDs. Counts are nonnegative JSON integers capped at JavaScript's exact integer limit; overflow is a safe server error rather than silent rounding. Durations/elapsed values are finite nonnegative numeric seconds. Missing timestamps/durations remain NULL; no NaN/Infinity or display-formatted numbers. `duration_seconds` is observed end minus start and remains NULL without both; `elapsed_seconds` uses end time, or the page's fixed `as_of` for an active collection row, clamped at zero. A detail response uses its request clock for an active row. Event counts describe visible **recorded** messages; zero is not proof that an event did not occur under a lower logging level.

C4a execution detail accepts only a strict positive BIGINT path ID and no query selectors. It is independent of overview filters and configured fixed dates. Read visible metadata before event work; absent and hidden IDs return the same safe 404. The second query rechecks execution visibility so retention or revocation between connections also returns 404. These observations are not a database snapshot. Reuse the list's exact identity/timestamp/code types; missing system logging metadata remains NULL, and unknown status/logging codes keep their numeric code with `name: unknown`. Duplicate system logging rows are a safe server error. All five `event_counts` use the categories below on full source text, including the documented collation-dependent heuristics; `all` includes other/unknown event kinds. `warning_count`/`error_count` equal `event_counts.warnings`/`errors`. No event text or parameter values are returned, and their disabled capability flags do not block these counts.

## Bounded pages and sorting

List-shaped resources default to `limit=50`, maximum 200; the legacy `EXECUTION_COUNT` does not override API limits. Fetch at most the page plus one sentinel row to derive `has_more`. No exact total is required per list/search request. A terminal page has `next_cursor: null, has_more: false`; otherwise both must indicate another page. `meta.from`/`to` are NULL for collections without a time filter. `meta.as_of` is fixed at first-page request time (separate from a historical `to`); `generated_at` reflects each response's observation time. No page is a database snapshot.

Folders/projects default to `sort=name&direction=asc`, with catalog collation and a same-direction ID tie-breaker. Each also supports its own ID sort (`folder_id` or `project_id`) and descending order. Names are non-NULL; navigation cursor v2 stores the exact name or decimal ID with a false NULL flag and binds the resource and exact folder scope. Continuations retain the first-page ceiling and `as_of`, with no time bounds.

Each list's sort keys/directions are enumerated in OpenAPI. Null sort values are last in both directions; the unique ID tie-breaker follows the selected direction. SQL uses fixed allowlisted expressions. C2a implements execution ID ordering; C2b implements created/start/end time, project/package/environment, status, logging, duration, warning and error ordering. Name sorts follow catalog collation with ID ties; status/logging sort by numeric code, durations/counts numerically, dates by their instants. A compound environment sort uses folder then name, with NULLs last for each component in both directions. A calculated sort computes its required key for the full matching cohort before paging. ID and base/date/name/status sorts retrieve counts and logging only for selected IDs; logging and count sorts reuse their precomputed key data. Duration uses actual end minus start, with a NULL key when either is absent; it never substitutes elapsed time. UTC seconds plus fractional ticks preserve 100-nanosecond order without a whole-duration nanosecond overflow. Never label sorting of the visible page as global sorting. `/meta` advertises only sorts actually implemented.

Use forward cursor navigation in the requested sort direction; changing direction starts a new paging session. Cursors are opaque versioned HMAC-authenticated tokens using a server-owned random per-process key initially. Bind resource/version, canonical exact/pattern filters, status, event search/category or values section, limit, sort/direction, effective bounds, authorization scope, initial `as_of`, upper ID, last raw sort key/null state and unique tie-breaker. Use digests for filter/search and authorization-scope binding rather than embedding raw search text or identities. Sort timestamps retain full SQL precision even if the browser parses fewer digits. No credentials, parameter/override values or event messages belong in a token. Maximum token length is 8192 characters and validity is 30 minutes from session creation, without sliding extension. Do not expose/reuse Flask's session secret or accept client-provided signing keys.

Execution cursor format v2 authenticates the raw sort-key list, explicit per-component NULL flags and the last execution ID. Numeric keys use decimal strings, timestamps use exact UTC strings and public name keys retain the catalog values shown in rows; filter and authorization bindings still use keyed digests. SQL compares those keys under the catalog collation, without a last-row lookup. Older cursor versions fail safely and require a fresh first page.

On continuation, repeat every non-cursor selector (defaults are allowed only when they equal the initial effective selection); the returned explicit `from`/`to` must be sent for a windowed collection. Omitting/changing them does not resolve a new clock bound for an existing cursor. Malformed/altered/wrong-scope or mismatched tokens return safe 400 `invalid_cursor`; expired tokens or a process restart may return 400 `cursor_expired`/`invalid_cursor` and require a fresh first page. Recheck SQL visibility and capability on every request. A signature never makes a cursor an authorization token. Shared-worker key coordination is deferred hosting design.

Capture an initial maximum visible execution/event/statistics/pre-event ID within the selected resource scope and exclude later inserts. Folders/projects use their ID ceiling; history uses execution IDs; parameter pages use execution parameter IDs and overrides use the public view's `property_id`. Long property paths therefore do not need to fit in a cursor or serve as invented identity. Override values are live observations, not frozen configuration history. An initially empty collection has `upper_id: null` and no continuation.

The ID ceiling prevents new inserts from entering a session; retention, visibility and existing-row status/count changes can still alter membership/order. Do not claim lossless traversal of mutable sorts. A detected relevant change invalidates the client page/cursor chain and calls for a fresh first page while preserving display preferences. Before phase 5 notifications, manual/data-only refresh starts a new session; clients must not silently stitch refreshed rows into an older chain. An exhausted/empty page under retention is valid and does not turn into 403. Never silently reuse a cursor across identity/policy changes.

Events support `kind=all|errors|warnings|duplicate-warnings|memory-warnings`, default `all`. Errors/warnings match `OnError`/`OnWarning`; duplicate warnings additionally match the legacy `duplicate` substring, and memory warnings match `OnInformation` plus `memory allocation`, using catalog collation. These last two are documented heuristics and may overlap other categories. `q` is a literal substring of full message text (1–512 Unicode characters and at most 1024 UTF-16 units). Search is case-insensitive using SQL `LOWER` under fixed `Latin1_General_100_CI_AS_SC`, followed by exact `Latin1_General_100_BIN2` substring comparison. It is accent-sensitive; `%_[]~`, quotes, backslashes and `*` have no wildcard meaning. This deliberately replaces the draft catalog-collation search: native legacy collations can ignore supplementary characters, matching unrelated text or missing an actual emoji. Request values stay bound parameters, with no SQL-text interpolation. Search/category filters apply before paging and over full source text even if the returned display text is truncated. Sort by message time then event ID, default ascending. The upper event ID excludes new events until refresh.

To keep single rows bounded, event `message` and parameter/override display `value` have a 16,384-character response cap; return the prefix and `truncated: true` when shortened, including for HTML-like text. Bound SQL result text projections as well as JSON output so an unbounded source value is not materialized through `fetchall()` just to be truncated afterward. Never cut a Unicode code point. Redacted NULLs are not truncated. Names/types/paths retain their documented schema bounds; oversized unexpected catalog fields fail safely rather than being silently reinterpreted. This is bounded browsing, not a bulk export endpoint.

C5 events accepts only `limit`, `cursor`, `sort=message_time|event_id`, `direction=asc|desc`, `kind` and `q`; default 50/time/ascending and max 200. The events capability guard runs before execution/SQL work, including HEAD and OPTIONS. Once enabled, visible-execution validation precedes event queries; fence/page SQL rechecks visibility. Category and full-source search precede the narrow candidate page; wide text/metadata is projected only for at most 201 selected IDs. No exact total is required. The cursor binds raw search/category through keyed digests, plus execution, order, limit, scope, initial time and the maximum matching numeric event ID. Changing any selector starts a new session. End-of-page retention is a successful empty collection; missing/revoked execution visibility is the common safe 404.

Public Scale Out event IDs can be NULL; the public GUID is nullable and the inspected Scale Out source indexes do not guarantee uniqueness. Numeric paging excludes these unidentifiable rows and explicitly returns `meta.has_unidentified_events: true` when any matching visible record lacks an ID, forcing `availability: unknown` even with an empty result or logging level none. Coverage is filtered by the same category/full-text search and rechecked on continuations. No GUID, row number, message hash or invented event ID replaces identity. `has_more` describes identified matching rows only; execution detail counts still include all recorded rows. Without unidentified matches, nonempty pages are `available`; empty pages are `not-recorded` only with system logging level none, otherwise `unknown`. Real Scale Out acceptance remains separate from synthetic NULL-ID/GUID coverage.

Event messages preserve NULL and empty text, literal HTML-like text, unknown SMALLINT message/source codes and NULL source types. SQL bounds the message projection to 32,770 UTF-16 units and removes a high surrogate only at a genuinely clipped edge; this retains a full Unicode-character sentinel beyond the 16,384-character response cap. Python validates the bounded prefix, emits at most 16,384 characters and sets `truncated` from actual character length. This avoids the measured native SC `LEFT` boundary defect with mixed ASCII/emoji near 64 KiB. Search and duplicate/memory heuristics still inspect full source text, including suffixes beyond the display prefix. Oversized metadata paths/names fail safely rather than becoming partial identities. Messages/search never enter application logs, errors or cursor payloads; enabled event responses intentionally contain authorized message text.

## Inspection, values and history

Execution details are independent of the overview time filter. Children are invocation observations inside the parent's execution, keyed by their pre-event ID, not new execution IDs. Match end events by path/source/occurrence as well as operation. An unmatched start is `state: incomplete` with NULL end/duration; never infer success. Executable results use 0 success, 1 failure, 2 completion, 3 cancelled and unknown fallback. Collection `availability` is `available`, `not-recorded` only with evidence of insufficient logging, or `unknown`; an empty result alone proves neither missing logging nor missing children.

C4c children accepts only `limit`, `cursor`, `sort=started_at|observation_id` and `direction=asc|desc`, defaulting to 50/start/ascending, with max 200. Validate the visible execution before child queries, recheck visibility in fence/page SQL, and bind the initial maximum child **start** ID, exact time/ID seek, execution, order, limit and SQL/policy scope into the cursor. Observations have non-NULL start times. New starts above the ceiling require refresh; end events above that ceiling can complete an existing observation. Retention, current end observations and availability remain live, not a frozen snapshot. Exhausting a visible page is 200; absent/revoked execution visibility is the common safe 404. These timing observations require no event-text or value capability and return neither messages, values nor internal source identifiers.

A child start is `OnPreExecute` at exact package path `\Package` with a nested execution path (a backslash after its first character). Pair only package-root pre/post events within the same execution and exact package name, execution path, source ID and nullable source type; binary comparisons plus lengths distinguish case and trailing spaces. On each identity's numeric event-ID order, a start completes only when its next event is a post, its preceding event is not another start, and the post time is at or after its start. Consecutive starts are ambiguous and remain incomplete rather than sharing/stealing an end. Missing package/source identity or an unorderable event on that identity also leaves it incomplete. NULL source names/types are preserved. `complete` means a timing pair was observed; it conveys no success result.

The public Scale Out event view can expose NULL numeric IDs. C4c cannot assign those starts the required pre-event ID or stable numeric cursor, so they do not enter `data`; `meta.has_unidentified_starts: true` explicitly reports visible qualifying starts without IDs and forces `availability: unknown`, including mixed or otherwise empty pages and logging level none. This flag is rechecked on continuations. No synthetic child execution/observation IDs are invented. Without such starts, observations yield `available`; an empty page yields `not-recorded` only with system logging level none, otherwise `unknown`. C5 uses the same explicit numeric-identity coverage boundary for events; GUIDs are not substituted for numeric IDs.

C4b executables accepts only `limit`, `cursor`, `sort=started_at|statistics_id` and `direction=asc|desc`, defaulting to 50/start/ascending. It reuses visible-execution validation before statistics queries; each query rechecks execution visibility, including continuations. Capture the maximum visible statistics ID within that execution on the first page, then seek with exact timestamp/NULL/ID keys. Cursor binding includes the execution ID and SQL/policy scope. A visible exhausted collection is 200 with no continuation; missing/revoked execution visibility is the common safe 404. New statistics above the ceiling require refresh, and retention or mutable observations are not a snapshot guarantee.

Select at most 201 narrow statistics rows before enriching paths/names. `execution_path` and `name` preserve catalog NULLs, as do missing executable metadata and unfinished timestamps/results. Keep repeated invocations as distinct `statistics_id` observations even when they share an executable. Derive actual seconds from both timestamps, preserving their seventh digit; never substitute the user-defined `execution_value` or confuse executable result codes with execution status. The API never selects/returns that value and needs no text/value capability. Paths allow 16,384 Unicode characters, while executable names retain the SQL 4000 UTF-16-unit bound; bound SQL projections while preserving every valid supplementary character, and fail oversized fields safely without returning a partial path. Availability is `available` when observations are returned. With no rows, only recorded system logging level 0 (`none`) establishes `not-recorded`; missing, other or custom logging levels leave `unknown`. A zero-length/exhausted page alone does not establish insufficient logging.

`/values?section=parameters|overrides` defaults to parameters. Each section is its own bounded collection/cursor and query; the UI fetches both when needed. Return `execution_parameter_id` for parameter identity and the original SQL type plus a display-safe string/NULL, not an arbitrary JSON encoding of `sql_variant`. Parameter ordering is execution parameter ID; override ordering is the public view's `property_id`. Override records include its `sensitive` flag and original property path. A catalog lacking required ID/sensitivity columns is an unsupported compatibility case to record, not permission to invent IDs or expose values without checking sensitivity. No flag or missing value authorizes decryption or guessing.

C6 accepts only `section`, `limit` and `cursor`. Both sections use fixed ascending numeric IDs, default 50/max 200, no overview time range, and separate fences/pages. A cursor binds execution, section, limit and SQL/policy scope; it carries only numeric identity keys, never property paths, parameter names or values. Retention can exhaust a visible page with 200/empty; absent/revoked executions retain the common safe 404. `meta.sort` is `execution_parameter_id` or `property_id` for its section and `direction` is always `asc`. Empty collections do not infer missing logging or claim a value was never set.

Each SQL page first selects at most 201 IDs, then projects metadata and permitted display values. SQL replaces sensitive values with NULL before display conversion; override SQL also applies the explicit display policy. Serialization independently checks the source Boolean flag and current policy, ignores any forbidden value even from a faulty adapter, and derives `redacted`/`redaction_reason` rather than trusting supplied markers. `sensitive` takes precedence over `policy`. Missing/invalid flags or required metadata fail safely. Unredacted NULL and empty strings remain distinct. Policy changes invalidate old cursors, including a change that would permit more data.

Parameter `sql_type` preserves the catalog's `parameter_data_type` label, including unknown future labels. SQL converts the bounded `sql_variant` to a string before ODBC; floats/reals use round-trip style 3, binary values use `0x` hexadecimal, and other types use style 126, preserving decimal scale and date/time fractional digits/offsets. Integers/booleans display as decimal strings (`0`/`1` for SQL bit). No Python stringifying fallback or inferred JSON value type is used. Override values already have catalog nvarchar(max) type and receive no fabricated parameter type. Their SQL prefix uses C5's Unicode-safe 32,770-unit bound before the 16,384-character wire cap. Names/type labels retain 128 UTF-16-unit bounds; property paths retain 4000. Enabled nonsensitive responses may contain authorized operational text; all application logs, problems and cursors exclude values.

History requires exact folder/project/package and defaults to the last 50 running/succeeded executions, descending execution ID. An explicit status selection may include other known outcomes. It has no implicit dashboard time filter and never uses wildcard package identity. History rows retain their real identity and actual timestamps; no heading may claim a different row limit.

C7a accepts only required `folder`, `project`, `package` plus optional `status`, `limit`, `cursor`, `sort=execution_id` and `direction=asc|desc`. Names use catalog equality, including its case/accent/trailing-space behavior; `%_[]~`, `*`, quotes and slashes remain literal. Bounds are 128 UTF-16 units for folder/project and 260 for package, without trimming or repeated decoding. Status defaults to canonical `(2,7)`; explicit selection accepts known codes 1–9, rejects duplicates and sorts codes for cursor binding. Default 50/max 200, both global ID directions, matching-ID ceiling and keyed exact-name/status/limit/order/scope binding apply. `from`/`to` are always NULL and date/pattern selectors are rejected. Missing/hidden named scopes return equivalent successful empty collections, not an existence-disclosing 404.

Candidate IDs are bounded to 201 before independent recorded warning/error aggregation, metadata and system logging lookup. The metadata read rechecks current SQL visibility after selection. Logging conversion explicitly guards system object type/name before integer conversion so an eager plan cannot convert an unrelated user string. Duplicate system logging rows fail safely. Text/value capabilities may remain disabled: history returns no event text or parameter/override values. Status, event counts and visibility remain live; retention/revocation can exhaust a chain and status changes below its ceiling can change membership. `as_of` remains fixed for active elapsed-time calculations across pages; `generated_at` is per response. C7b reads visible successful-run IDs/timestamps through the latest page start once into a connection-local indexed source, then aggregates only each target's latest five samples. This narrow source can grow with prior history; it has no event/logging/value enrichment or whole-history duration aggregation. Estimates never replace NULL actual end/duration.

An estimate uses up to five completed successful runs of that exact identity whose end is at or before the target's start, excluding the target. Choose the most recent by `(end_time DESC, execution_id DESC)`, require both timestamps and nonnegative duration, and take the arithmetic mean in seconds. Samples are independent of the page's status filter and execution-ID ceiling. Include zero durations in the sample; if the mean is zero, no sample exists or the target has no start, return `estimate: null`. Otherwise return `method: mean_last_5_successful`, sample count, estimated duration and `target.start + mean` as a separate estimated end. Keep integer 100-nanosecond duration totals until calculating the mean; round only the estimated end to the nearest 100 nanoseconds, with half ticks rounded up. A positive mean below half a tick can therefore have the same estimated end as the start. If the estimated end exceeds the supported UTC year 1–9999 range, return `estimate: null`. This rule prevents future-run leakage into a past estimate; it does not promise prediction accuracy. Restrict all samples to visible catalog rows; retention, status changes and current permissions can change an estimate between pages. No historical account-visibility snapshot is implied.

## Errors and health

Use RFC 9457 `application/problem+json` with `type: about:blank`, standard status title, matching numeric HTTP status, a fixed safe detail, a stable `code` and `request_id` matching the response header. Omit `instance` and rejected values so an error does not echo a URL, search, cursor, secret or SQL diagnostic. Unknown paths **within the API namespace**, malformed ID paths and method errors are JSON, even when Flask has no matched blueprint; unrelated legacy failures stay HTML. Successful scoped emptiness is 200, not a database failure disguised as empty data.

| HTTP | Code / meaning |
| --- | --- |
| 400 | `invalid_input`, `invalid_cursor` or `cursor_expired`; unsupported/malformed request, excessive range/buckets or invalid paging session |
| 401 | `unauthenticated`; reserved for a future configured authentication boundary with its real `WWW-Authenticate` challenge; local mode does not manufacture a login requirement |
| 403 | `forbidden`; endpoint capability denied, before catalog queries |
| 404 | `not_found`; unknown resource or absent/not-visible execution, with the same safe detail |
| 405 | `method_not_allowed`; preserve `Allow` |
| 500 | `internal_error`; unexpected/conversion/query-permission/cleanup failure, with no driver diagnostic |
| 503 | `database_unavailable`; existing safe connection/authentication/driver SQLSTATE mapping |
| 504 | `database_timeout`; existing HYT00/HYT01 mapping |

`/healthz` checks process liveness with zero database queries. `/readyz` performs one zero-row catalog read in the configured SSISDB, independent of execution visibility/count. `API_READINESS_TIMEOUT_SECONDS` defaults to 2 and accepts integers 1–2; each driver login/query timeout is the smaller of this cap and its global database timeout. These are driver limits, not a promise of a two-second total HTTP deadline. It exposes only ready status or the common safe error shape. Neither returns connection/identity/server information or replaces a workflow/native/hosting check.

C1c's shared input layer decodes query encoding once with strict UTF-8, rejects malformed percent escapes, duplicate/unknown/empty keys or values and NUL, and rejects GET/HEAD bodies before any catalog call. Registered resources declare accepted query keys. Metadata/health accept none; executions accepts the documented name/pattern, status, window, limit, cursor and ID-order selectors. C2a implements cohort resolution, escaped patterns, startup fixed-date DST validation and authenticated cursors, using the shared integer/ID/name/status/timestamp helpers. Unknown routes under `/api/v1` return JSON 404; HTTP 405 preserves `Allow`. The local mode has no login requirement; a future authentication boundary's real 401 challenge is preserved by the common renderer.

## Validation and remaining gates

The implemented C1b boundary is [exact timestamps](../dashboard/timestamps.py) plus [explicit serialization primitives](../dashboard/serialization.py). New queries opt into `execute_query(..., typed_timestamps=True)`; legacy queries retain their default results. Bind parsed instants with `sql_timestamp()` and an explicit `CONVERT(datetimeoffset(7), ?)` in checked-in SQL; passing a Python datetime to ODBC would lose the seventh fractional digit. Use serializers before JSON encoding, without a generic `default=str` fallback. Resource DTO assembly, query shapes and HTTP validation remain their own milestones. The native converter follows pyodbc's [connection-local output-converter interface](https://github.com/mkleehammer/pyodbc/wiki/Using-an-Output-Converter-function).

C1a checks the document/schema, references, examples, parameter/resource coverage and policy alignment only. Install the tracked [development requirements](../requirements-dev.txt) and run `python -m unittest discover -s tests -v`; [contract tests](../tests/test_api_contract.py) run without any ignored tooling. The OpenAPI draft uses 3.1.1/JSON Schema 2020-12; schema validation does not run Flask, SQL or implement authorization. Separate [timezone tests](../tests/test_timezones.py) cover startup validation and packaged-data DST transitions. C1b owns native datetimeoffset proof; C1c owns parsing/error/capability implementation; resource milestones own independent SQL/actual-reader comparisons; C8 owns combined acceptance. B5a3/P0b and the five incomplete backend checklist cases retain their recorded status. Production hosting and SSE remain deferred/separate delivery gates.
