# Modernization plan

[The roadmap](roadmap.md) defines scope. [Progress](PROGRESS.md) owns milestone status and open gates; [API semantics](API_CONTRACT.md) and [OpenAPI](openapi.yaml) own the interface. This document records architectural decisions and future delivery boundaries.

## Architecture

Keep Python, Flask, pyodbc and useful checked-in SQL. Serve a read-only API and prebuilt browser assets from the same application origin. Organize functions around operations; introduce a class only when its state and lifecycle belong together. No ORM, extra application database or framework migration is required.

## Data and legacy boundary

Keep the legacy adapter alongside the new API until replacement-screen parity. The API corrects mixed time cohorts, wildcard sentinels, formatted string types and unbounded reads; these corrections do not silently change the legacy parity baseline. Preserve actual NULL timings and unknown numeric codes. Child invocations are observations, and estimates remain separate from actual timing. [API semantics](API_CONTRACT.md) owns the detailed rules; [the operation matrix](API_ACCEPTANCE.md#operation-matrix) checks them.

## SQL and resource decisions

Ordinary execution sorts must seek/select the bounded page before metadata, logging and event enrichment. Global calculated sorts may calculate keys over the whole cohort; prefer narrow working rows where measurement supports it. Keep event aggregation isolated from unrelated joins. A bounded result does not bound source scans, repeated-key windows, permission checks or history-source growth.

Current measured choices—narrow calculated cohorts, cached ID selection/logging and constrained event join order—are recorded with their tradeoffs in [the SQL remedy results](API_ACCEPTANCE.md#c82b3-execution-query-remedies).

Validate source and temporary scans, actual rows, logical/LOB reads, materializations, spills, compilation, response size and elapsed time under representative identities. Retain verified reductions in work despite noisy small-catalog latency unless they cause a material regression or disproportionate complexity. Apply RECOMPILE only to query shapes with measured justification. Do not modify system indexes, use internal-table permission shortcuts, introduce NOLOCK or hide unmeasured work behind a result cache. [The workload protocol](API_ACCEPTANCE.md#workload-protocol) defines comparable measurements.

Preserve parameter binding, exact 100-ns timestamps, BIGINT strings and explicit serializers. Typed calls use the connection-local datetimeoffset converter; bind `sql_timestamp()` strings with `CONVERT(datetimeoffset(7), ?)` to preserve the seventh digit. Opt into explicit NULL binding with `declared_parameters=True` only when SQL declares every input type; retain legacy defaults for legacy queries. Each query closes cursor and connection, attempts both closes after failure, and records safe metadata after cleanup. Browser cancellation does not guarantee native SQL cancellation; driver timeouts and request/resource tests remain necessary.

## Frontend and dependency policy

Use vanilla ES modules, native DOM/events/fetch, semantic HTML and authored CSS. Vite is allowed for development and builds; additional chart/table libraries require a demonstrated benefit in interaction, accessibility, maintenance, size and lifecycle behavior, with licensing reviewed. Pin tools and bundle dependencies locally. Production makes no public font/script/analytics requests. Keep labels concise and pages functional, without decorative copy or animation.

Native frontend changes target APIs that reached Baseline by the end of 2025, without older-browser polyfills (user decision, 15 November 2026). ### Overview state and refresh

Organize modules around shared operations and lifetime, not a domain class hierarchy. `overview.js` owns applied selection, effective bounds, cursor paths, data requests and generations; renderers own DOM projections. `refresh-loop.js` owns one schedule and observes completed cycles without making data requests.

Keep draft filter inputs, applied selection and display preferences separate. Shareable URLs contain validated selection/sort/limit and relative preset tokens only. Exact catalog names are neither trimmed nor normalized; omitted scope means all, while a literal `all` remains selectable. Canonical names live in the selection session because single-line inputs can strip characters. A folder change clears its dependent project; exact row links set both names together. Status commits on Done/outside/Tab close, Escape discards its draft, presets apply immediately and custom dates use Use range. Reset keeps scope/order. Invalid URLs clear the view and expose an explicit reset.

Catalog pickers are lazy and independently cancellable. Browse at metadata `default_limit`; debounced search scans at `max_limit` within `20 * default_limit` rows per action, rounded to whole pages. Partial results require explicit continuation. Project browsing requires a folder, while exact-name entry can span folders. Each request has a 15-second deadline; close/replace/dispose aborts it and rejects late results. Expiry requires a manual restart and denial clears choices. Continuation focus respects user movement.

Created bounds use the configured display timezone. Date-only ranges include both dates; timed upper bounds are exclusive. Reject DST gaps and require explicit repeated-time occurrence. Preserve untouched exact offsets/seven fractional digits and track edits per bound. Relative `created=24h|7d|30d|180d|today` uses a metadata/list server anchor plus monotonic elapsed time, not client wall time or an extra metadata read per cycle. Custom/bookmarked bounds stay absolute; omitted bounds retain server-default semantics.

A normal overview cycle serially reads executions, all-status summary and the timeline only when open. The list supplies exact effective `from`/`to`; cards use those bounds but ignore the selected status. Timeline uses the list's folder/project/status and bounds, without list order/limit/cursor. These are live observations, not one atomic database snapshot. Each overview request has a 30-second deadline. Execution failure prevents subsequent reads; summary failure is independent and may still be followed by the timeline. Summary Retry rereads summary and an open timeline without another list.

Schedule after the entire cycle, with delay `min(300000, max(30000, ceil(cycle_ms * 5), failure_backoff_ms))` and transient backoff 30/60/120/240/300 seconds. Success resets failures; nonretryable errors stop automation. Manual work stays immediate and replaces the timer; repeated activations during active work coalesce. ## Production live updates

SSE is the initial server-to-browser transport; WebSockets require a concrete bidirectional need. The transport and SSISDB change detector are separate responsibilities.

1. Use shared bounded/timed change detection per approved database/authorization scope. Detect new records **and updates to existing active executions**; a maximum execution ID alone misses transitions. Never keep an ODBC connection for the lifetime of a browser stream.
2. Own detector startup/shutdown explicitly and avoid debug-reloader duplicates. Define coordination before adding multiple workers; process-local queues do not provide cross-worker continuity, and paging cursors need one shared `API_CURSOR_SECRET_KEY`.
3. Send small authorized resource-change notifications, without raw messages, values or connection details. Coalesce client refetches and recheck subscription access on reconnect or identity expiry.
4. Define ordered event IDs, bounded replay and idempotent handling. Snapshot/subscription handoff must not lose changes. Unknown/expired IDs, restart, retention gaps and queue overflow require explicit resync.
5. Bound queues, subscribers, replay and message sizes. Disconnect or resync slow clients, send heartbeats, and release subscriptions on disconnect/navigation/shutdown.
6. Show connecting/live/reconnecting/paused/stale/polling state. Hidden-tab return requires resync. Fall back to data-only polling with backoff and no overlapping loops; stop polling when streaming recovers.

**P5.1 local detector (implemented 7 November 2026).** `dashboard/changes.py` holds pure state; `dashboard/detector.py` owns one polling thread per application, disabled by default (`CHANGE_DETECTION_ENABLED`). Execution IDs are operation IDs (deployments, validations and other operations share the sequence), so the high-water mark is an operation ID.

A seed (`detector-seed.sql`) takes the highest visible operation ID and, bounded by it, at most 257 of the newest active executions (statuses 1/2/5/8; 256 are kept and a 257th marks an overflow), the committed IDs among the newest 256 operation IDs, and which of the replaced state's unexpired gaps have committed. The committed IDs are read in a statement before the active executions, so within the newest 256 IDs and the carried gaps an ID that either read finds is covered by the seed's `resync`, and only an ID that neither read finds becomes a gap; IDs above the mark are left to the first poll. No status index exists, so finding the active executions can read every execution up to the mark. The detector reseeds at start, after an outage longer than the gap window, after a poll returns unexpected rows, and, while the state is incomplete, at most once per gap window. Each poll is one database call (`detector-poll.sql`): it stores an XML list of at most 512 tracked IDs and the next 201 operation IDs above the mark, then looks up executions among both. The candidate IDs are bounded and the measured plans look each one up by key; 512 tracked IDs cost 983 logical reads at 20,000 executions and 1,454 at 100,000 ([P5.1b receipt](API_ACCEPTANCE.md#p51b-change-detection-sql-work-7-november-2026)). Each poll opens and closes its own logical connection through `execute_query`; as for all queries, ODBC pooling decides how many physical sessions stay open.

Tracked IDs are active executions and ID gaps (IDs below the mark that no visible operation holds yet, because a lower ID can commit after a higher one). Ordinary polls re-read gaps for at least three poll intervals (at least 60 seconds) and drop them only after a final read; a reseed covers only the unexpired ones and the newest 256 IDs. More unresolved gaps than fit, or more active executions, mark the state incomplete with a `resync`. After a gap overflow, or a reseed whose mark moved more than 256 IDs past the previous mark, untracked IDs may still commit, so the state stays incomplete until one gap window has passed; only then can a reseed make it exact again. A failed seed keeps the previous state. Notifications carry only execution ID, status code and end time: `created`, `changed`, `removed` or `resync`. Terminal executions are assumed not to change again. An ID that commits after its gap's last successful read gets no `created` unless a later poll or reseed still covers it; when an outage ends in a reseed that does not, this includes a commit before the gap's expiry. A cycle reads at most five pages and publishes each page at once; a backlog continues without waiting.

Events enter a bounded log with increasing sequence numbers. Subscribers hold a cursor `<generation>:<sequence>`, where the generation is random per detector instance; `read(after, timeout)` returns later events and one cursor for the end of the batch without touching the database, or `resync` for no cursor, a cursor from another instance (a restarted process), one newer than the log or one older than it. A subscriber's `resync` reads no SQL; only the detector's own reseed does. The log keeps private copies of the events, and `poll_once` and every `read` hand out the caller's own, so one consumer annotating an event cannot change another's replay. `runserver.py` resolves debug once (as `app.run` does with `FLASK_DEBUG`) and passes it to both the reloader and the detector guard, so the reloader's watcher process never starts a duplicate. Transport, authorization scope per subscriber and multi-worker coordination remain P5.2 decisions under the hosting hold.

**P5.2 decision record (8 November 2026, revised 20 November 2026).** These decisions fix what a stream must do on top of the P5.1 detector. They implement nothing; the transport and every production check stay under the hosting hold. The 20 November revision follows a second independent review against the detector as of `69d2d33`.

1. **Transport and frames.** One SSE resource, `GET /api/v1/changes` (`text/event-stream`), notification-only. No WebSocket: nothing flows from browser to server except the reconnect cursor. Status, end time and everything else come from the client's refetch through the existing read operations, under the identity's visibility at that moment. Output is UTF-8 without a byte-order mark. A frame has `event:`, at most an `id:` line and one `data:` line holding a JSON object, and ends with a blank line; a frame without `data:` dispatches nothing to the page. Heartbeats are comment lines, which scripts cannot see. A stream that ends by its own limit sends `retry:` first, in ASCII decimal milliseconds.

   The stream picks its frame by the first matching row, when it opens and each time `read()` returns:

   | Condition | Frame and `data` | `id` | Client action |
   | --- | --- | --- | --- |
   | Detector stopping, stopped or unhealthy (item 3) | `stale` `{"reason": ...}`; the stream then ends | empty, which clears the browser's cursor | poll (item 7) |
   | Opening with no cursor or a malformed one; any `read()` that returns `resync` (another generation, a cursor newer or older than the log, including a log trimmed past an open stream's cursor); or a batch holding the detector's own `resync` event (a reseed or an overflow) | `resync` `{"reason": ...}` | the cursor that `read()` returned | reload what it shows |
   | A batch with events | `changes` `{"ids": [...]}` or `{"ids": null}` | the batch-end cursor | refresh (item 7) |
   | Opening with a valid cursor and nothing new | `changes` `{"ids": []}` | the same cursor | count the stream as live; no refresh |
   | A later read that times out empty | comment heartbeat | none | none |

   Exactly one frame opens each connection. Reasons come from a closed list. `ids` holds the distinct execution IDs of the batch as decimal strings, or null, which asks for a refresh of everything shown; for a batch with events it is null when the batch holds a `removed` event, when it exceeds a size budget, and in anonymous mode (item 2). The opening `{"ids": []}` is the same in every mode. The stream checks a cursor's format itself, because `read()` raises on a malformed one. A browser takes a frame's `id` as its cursor only when it parses the frame's final blank line, so a connection cut before then reconnects from the earlier cursor; while that cursor can still be replayed, the next read covers at least the same changes, possibly in a larger batch, and otherwise it returns `resync`. Per-event cursors are therefore not needed.
2. **Replay, handoff and disclosure.**
   - **Replay:** the bounded log and nothing else. The detector also replays from exactly one position before the oldest entry.
   - **Snapshot handoff:** the client first takes the cursor from the opening `resync`, then loads, then treats later frames as refresh requests. Refetches are idempotent, so a frame that duplicates the load is harmless, and none can fall between the cursor and the load.
   - **Disclosure:** a `removed` event is never named. `removed` exists only for tracked active executions, so a terminal execution that becomes invisible to the detector's SQL identity produces no event, and its earlier `created` stays in the log until the log's count bound trims it; a new subscriber can then receive an ID that became invisible before it connected. That the same identity could once read the row does not make this acceptable by itself. Until the user decides that frames may name execution IDs on a given catalog, the stream runs in anonymous mode, where every `changes` frame for a batch with events is `{"ids": null}`.
   - **Revocation:** a subscriber's access is checked when a stream opens. A stream ends at the earlier of its lifetime and a known expiry of the subscriber's authorization; bytes already buffered on the path can still arrive after that. A change of a detector's authorization scope starts a new log generation and ends the streams opened under the old one. The acceptable delay is set by the hosting permission policy.
3. **Stream lifetime, health and capacity.** A stream holds a server thread but no database connection: it waits on the detector's condition, never on SQL.
   - **Lifetime and heartbeat:** each stream ends after a bounded lifetime (a few minutes), so the browser reconnects with its cursor and access is rechecked. A comment goes out between frames at a fixed interval below the shortest idle timeout on the path.
   - **Detector health:** healthy means the thread is running and not stopping, the state is seeded and complete, and a poll (not a seed) has succeeded since the latest seed within a freshness bound (a few intervals). An incomplete state (an active or gap overflow) is unhealthy until a reseed restores it and a poll succeeds, because notifications can then miss changes. Before any transport, the detector must publish this state, including the monotonic time of that poll, together with the cursor under the condition lock, and `stop()` must mark the detector stopping under the same lock and wake readers. Today `status()` cannot serve: a seed also sets the last-success time, a reseed after a bad poll clears `failures`, these fields are written outside the lock, and the thread still runs during a stop.
   - **Health on a stream:** `read()` does not return when a poll finds nothing or health changes, and while a detector stops it returns empty batches at once. The stream therefore opens with `read(after, 0)`, then calls `read()` with the shortest of the heartbeat interval, the remaining lifetime and the time left before a known authorization expiry as its timeout. It applies the frame table at each return and checks both deadlines again before sending; a stopping detector ends the stream.
   - **Slow clients:** a stream ends, with `retry`, before its output reaches the server's output-buffer limit. That bounds the bytes buffered for it, but a full socket can still block a write. The enabling gate for a serving stack is a test on the chosen server and proxy with compression and response buffering off for this resource. A slow reader and a reader that stops reading must each produce back-pressure. A stream that cannot write within a progress deadline must be terminated, and within a reclaim deadline after a stream ends its subscription slot, thread, socket and buffered bytes must be back at baseline, counted directly. Ordinary API latency must stay within budget meanwhile. The `request_completed` log line is written before the generator runs and proves none of this. Waitress 3.0.2 specifics: `outbuf_high_watermark` counts every pending byte, including headers and chunk framing; `channel_timeout` skips connections with a request in progress; the deprecated `send_bytes` above its default of 1 can hold back small heartbeats. Until the gate passes, streaming stays disabled on that stack.
   - **Server cap:** concurrent streams are capped per process below the server's thread count, so ordinary API requests keep threads. The slot is taken without waiting; over the cap, the server answers 503 before any frame (with `Retry-After` for non-browser clients; `EventSource` cannot read response headers). One release operation, which acts once, runs both when the generator finishes and when the response closes; a normal end, an early disconnect and a response never iterated must each return exactly one slot.
   - **Browser connections:** over HTTP/1.1 a browser opens about six connections per host, shared by all tabs. A stream can wait for a connection, which the handshake timeout of item 7 covers; snapshot and refresh reads can also queue behind streams that are already open, inside the browser where no 503 is visible, which that timeout does not cover. With 1, 6 and 7 tabs, every snapshot and refresh must obtain a connection within a deadline. The means (fewer streams per browser, one stream shared between tabs, closing an open stream when data reads starve, or HTTP/2) are chosen after the prototype.
   - **Budgets:** the lifetime, heartbeat, freshness bound, server cap, log size, `ids` size bound, handshake timeout, progress and reclaim deadlines and calibration interval become measured budgets after a prototype, as the roadmap requires.
4. **Endpoint contract and admission.** Before implementation, [the API contract](API_CONTRACT.md) and `openapi.yaml` describe the resource.
   - **Success and errors:** success is `text/event-stream` with the frames of item 1. Errors are returned before any frame in the existing JSON envelope; capacity has its own 503 code, distinct from `database_unavailable`. Responses keep `Cache-Control: no-store` and the request ID.
   - **Flag:** the stream has its own flag, which requires `CHANGE_DETECTION_ENABLED`; `/meta` reports it, which changes the capabilities schema. With the flag off the client polls and never opens a stream.
   - **Request handling:** the view finishes the Host, Fetch Metadata, capability, cursor and slot checks before the response starts, and copies what it needs from the request. HEAD and OPTIONS run the checks without taking a slot.
   - **Admission:** a browser request needs `Sec-Fetch-Site: same-origin`; the same-site and navigation exceptions of `/api/v1` do not apply, because different ports on one host are same-site but not same-origin. Requests without Fetch Metadata are admitted as for `/api/v1` and count against the same cap. Whether the other API routes tighten likewise stays Q7 in [Progress](PROGRESS.md#next-actions). A shared deployment also needs concurrency and connection-rate limits per authorized principal or scope.
5. **Authorization scope.** One detector serves one SQL identity; in the current mode that is the process's configured identity, so notifications cover only executions that identity could see when the change was detected, and every refetch applies current visibility. The stream carries no event text or values, so the events/values capabilities do not gate it. One shared SQL identity cannot give users different SQL rights; endpoint authorization can still narrow who may subscribe. If a hosting design introduces endpoint authorization or delegated identity:
   - detectors are keyed by approved SQL scope rather than by browser user;
   - a subscriber's scope is resolved when the stream opens and rechecked at each reconnect;
   - item 2 bounds how long a revoked viewer keeps receiving notifications.
6. **Workers.** Streaming supports one serving process with threads, which owns the only detector. With several worker processes, each would poll SSISDB (load × workers), and a client moving between them would get a `resync`. That stays correct but is noisy, so multi-process serving needs a measured load first, and sticky routing is decided from that measurement. A shared coordinator (an external broker or a database table) would add a dependency and is not chosen; it would need its own decision. The detector, its log and its generation must be created in the serving process: a host that loads the application before forking workers would give every worker the same generation, so a cursor from one worker could be accepted by another for different events. Change cursors are positions, not signed tokens; `API_CURSOR_SECRET_KEY` signs only paging cursors. `dashboard/wsgi.py` creates but never starts the detector, so each production server needs an explicit start/stop hook in the hosting design, as `runserver.py` provides locally.
7. **Client.**
   - **Refresh on a frame:** the overview, detail and History refresh owners treat a frame as a request for their existing in-place refresh, preserving selection, paging, scroll and focus. Overview and History refresh on a `resync` and on a `changes` frame whose `ids` is null or not empty; a detail page refreshes on a `resync` or when `ids` names its execution or is null.
   - **Pending flag:** each owner keeps one for its current page and selection. A frame that asks that owner for a refresh sets it; only a refresh that started after the frame and succeeded clears it. A frame that arrives during a refresh or the initial load causes exactly one more coalesced refresh afterwards. At most one refetch is in flight. A failed refresh leaves the flag set, the existing refresh scheduler retries with its backoff, and further frames do not bypass that backoff. Before each refresh the owner rechecks pause, visibility, a terminal detail and disposal. Owners must report success explicitly, because some (History) resolve their promise after a handled failure.
   - **What the stream does not cover:** it tracks execution lifecycle (membership, status, end time) and nothing else. New events, warnings, errors or executables inside a running execution do not change its status. While a page shows an active execution, its existing timed refresh therefore continues. Overview and History otherwise get a slow calibration refresh (a budget after the prototype), which also corrects the item 8 limits within their bounds.
   - **Eligibility:** frames, fallback polling and calibration all obey the existing pause and eligibility rules. A paused page or hidden tab refreshes on none of them. A detail page whose execution has ended keeps today's rule (manual Refresh and section actions only; see above); a frame for its execution restores nothing that the existing running-read rule does not.
   - **Connection state:** the client shows connecting / live / reconnecting / paused / stale / polling. A stream is live from an opening `resync` or `changes`; an opening `stale` means polling. After an `error` event it is reconnecting until its next frame. A hidden tab closes its stream; on return a new `EventSource` without a cursor opens with `resync` or `stale`. Without an opening frame within the handshake timeout, the client closes the stream and polls.
   - **Browser behaviour:** when a 200 stream ends normally, the same `EventSource` fires `error`, enters `CONNECTING` and reconnects with its last event ID. A final non-200 response (after redirects, including 204 and 503) or a wrong media type closes it for good, and scripts can read only `readyState`, never the status or headers.
   - **Fallback and recovery:** the client owns recovery with its own backoff. When the stream is unavailable (closed by a non-200, `stale`, handshake timeout, repeated errors), the client closes its `EventSource` and resumes data-only polling with backoff. At each backoff step it probes with a new `EventSource`, at most one at a time; with the flag off it never probes. `EventSource` shows a 403 exactly like a 503, so the scheduler's 401/403 stop rules apply only to data reads, whose status is visible. When the current probe fails while the page may still recover (not hidden, disposed or replaced), the client sends a same-origin `HEAD /api/v1/changes`, which runs the admission checks without taking a slot (item 4): a 401 or 403 there stops probing, and any other result keeps the backoff. The request is cancelled, or its result ignored, once the page is hidden or disposed or a newer probe starts. A probe that opens with `resync` starts the resync refresh. Polling ends only if that refresh succeeds while the probe is still the current connection, has received no later `stale` or error, and the page selection is still the one refreshed; otherwise polling continues.
8. **Known limits carried from P5.1.** Changes these may miss: an untracked ID outside the first seed's lookback (at least 256 below its mark) that commits later; an ID that commits after its gap's last successful read when no later poll or reseed covers it (after an outage, also before the gap's expiry); a terminal execution that changes again or is deleted by retention; a tracked active execution that disappears (a `removed`) and later becomes visible again; and states that begin and end between two polls (a refetch reads the current state). Overview and History refresh a later page within its original `upper_id` and `as_of` bounds, so the calibration refresh corrects only what falls inside the page shown. New IDs become eligible once page one is reloaded or Latest is chosen, and where they appear depends on the filter and sort. A detail page whose execution has ended corrects them only on manual Refresh, as today.

Open decisions for the user:
- whether to allow a loopback-only, default-off stream prototype while hosting is on hold (the roadmap currently keeps SSE transport under the hold);
- the budget values in items 3 and 7, which need that prototype's measurements, together with the roadmap's detector load and latency, queue and replay, and stream-versus-API concurrency budgets;
- how a browser with several tabs shares connections (item 3), after the prototype;
- whether frames may name execution IDs on a given catalog (item 2; anonymous until decided);
- the authored-size budget before P5.2 (D6/Q3) and Fetch Metadata for the other API routes (Q7), both in [Progress](PROGRESS.md#next-actions).

The hosting permission policy decides the acceptable revocation delay (item 2). Topology, identity and the proxy remain hosting decisions. SSE as the first transport is decided by the roadmap.

A prototype needs the detector health state of item 3 and nothing else from the detector. It should at least measure:
- recovery: disconnects after a frame's `id:` and `data:` lines but before its blank line, and after the blank line; a generation change, log overflow, `removed`, a reseed after a bad poll, a frame during the first load, a failed refresh, a `stale` during a probe's refresh and hidden-tab return. Every covered change must lead to a successful refresh or a `resync`; count extra refreshes and the time from a change to a successful page refresh;
- capacity: 1, 6 and 7 visible tabs, with streams opening before and after the snapshot reads, for browser queueing, ordinary API latency, 503 counts and threads in use, with detector reads counted apart from page refetches;
- transport: time to the opening frame, heartbeat spacing, reconnect after a normal end, slot release on each way a response ends, and the reclaim time after a reader stops.

On the chosen authenticated proxy and production server, repeat the item 3 gate and validate URL prefixes, idle timeouts and stream/API capacity. Development HMR and an ordinary polling screen do not satisfy this production milestone.

## Identity and hosting

G02 adds an explicit read-only `/api/v1/server` operation for the same SQL server label already displayed by legacy. It uses the configured SQL identity and existing Host/Fetch Metadata/error/logging boundaries; it returns only the server display name, never a login, service name, connection string or credentials. `/meta` remains database-free and identity-free. Each native mount reads the label once with a separate bounded/cancellable owner; its failure displays an unavailable label without blocking the screen or starting retries/polling. The application version comes from the same server version constant as metadata. This restores operational context without adding identity queries to overview/detail/history refresh cycles.

Scoped review aligns the label with legacy's `@@SERVERNAME` / SQL Azure `DEMO` expression. Recovery focus uses a visible section toggle, or the table region when that toggle is hidden on standalone History. A focused Pause disabled by an observed execution end moves to Refresh; retained Pause focus revalidating a terminal execution uses the same enabled target. Focus moved elsewhere by the user is preserved. These are presentation fixes, independent of polling, paging, authorization and protected-data lifetimes.

G05 retains legacy routes and uses Flask URL generation for every authored legacy asset/navigation link. Names containing decoded `/` or `\` use strict `/legacy/overview` and `/legacy/history` query-selector aliases; the original handlers now decode once. Aliases preserve legacy LIKE/status/100-unit semantics, reject unknown/duplicate/malformed inputs and keep selectors when unsupported conversion returns to legacy. Exact native overview conversion remains conservative; history conversion uses its separately approved LIKE scope. Neither mapping path queries SQL or chooses an execution as an authorization proxy.

Local development binds to `127.0.0.1`. Shared hosting requires an approved audience and authenticated HTTPS proxy, no direct-access bypass, and an explicitly approved SQL read scope. A shared SQL account exposes its scope to authorized viewers; per-user rights require endpoint authorization or designed identity delegation. A browser login alone does not change SQL identity. Trust proxy headers only through the configured boundary and avoid wildcard CORS and cross-user result caches.

API events and values are disabled by default; overrides have an additional display policy. Sensitive values remain NULL in both SQL and serialization. These flags govern API routes; legacy coexistence retains its previous SQL-identity access. Host/access/startup logs need their own review in addition to safe application logs.

Hosting is deferred by the user's 15 October 2026 instruction. When resumed, select a supported server/proxy/runtime combination, certificate trust and service identity; repeat native checks under that identity. Waitress is a Windows candidate requiring stream-capacity validation. An ODBC Driver 18 migration must explicitly review encryption/certificate settings. Optional containers need a current supported OS/driver recipe; the legacy Ubuntu/Python image is not current acceptance evidence.

## Acceptance targets

Contract and native checks cover exact-name/time/status cohorts, both global sort directions, ties/NULLs, Unicode, large IDs, precise offsets/DST, live retention and permission changes, redaction, missing observations and safe failures. Browser checks cover deep links/back-forward, keyboard/narrow layouts, literal text rendering, stale-response races and preserved state. Stream checks cover the handoff/replay/resync/cleanup cases above on the real proxy. A plain SQL Server instance without representative SSIS Catalog data is not equivalent integration evidence.

[The roadmap](roadmap.md#acceptance-budgets) owns enforced frontend size ceilings and proposed latency budgets. [API validation](API_ACCEPTANCE.md#workload-protocol) defines the distinct SQL, WSGI and network measurements; production stream budgets require the chosen host.

Before shared deployment, resolve audience/read scope, required SQL/ODBC/platform matrix, authentication/certificates, proxy/server capacity and any local legacy customizations. Preserve Apache-2.0 and dependency attribution.
