# Modernization plan

[The roadmap](roadmap.md) defines scope. [Progress](PROGRESS.md) owns milestone status and open gates; [API semantics](API_CONTRACT.md) and [OpenAPI](openapi.yaml) own the interface. This document records architectural decisions and future delivery boundaries.

## Architecture

Keep Python, Flask, pyodbc and useful checked-in SQL. Serve a read-only API and prebuilt browser assets from the same application origin. Organize functions around operations; introduce a class only when its state and lifecycle belong together. No ORM, extra application database or framework migration is required.

| Boundary | Responsibility |
| --- | --- |
| `dashboard/__init__.py`, `config.py` | Application construction and private configuration |
| `api.py`, `api_validation.py`, `errors.py` | HTTP inputs, capabilities, safe response/status handling |
| `frontend.py`, `templates/app/` | Native shell, validated packaged-entry assets, prefix-aware bootstrap URLs and build-failure response |
| `executions.py`, `navigation.py`, `metrics.py`, `timeline.py`, inspection/event/value/history modules | Resource-specific query coordination and DTO assembly |
| `db.py`, `query/` | Bound SQL, timeout settings and ownership of each connection/cursor |
| `timestamps.py`, `serialization.py`, `cursors.py` | Exact typed data, explicit JSON primitives and authenticated paging state |
| `ssis.py`, `views.py`, templates | Retained legacy presentation adapter |
| `web/` and `dashboard/static/app/` | Browser source/build inputs and ignored generated assets included in prepared deliveries |
| `web/src/api.js`, `bootstrap.js`, `display.js` | Same-origin requests and safe errors; metadata startup lifetime; typed display without changing wire values |
| `web/src/selection.js`, `navigation.js`, `filters.js` | Exact selection validation and draft/applied state; bounded choice requests; table order controls; form/history bindings and teardown |
| `web/src/overview.js`, `render-overview.js` | Current overview request generation, exact-bound resource sequencing, typed response checks and native DOM presentation |
| Future update detector/stream modules | Change detection, subscription ownership, bounded notifications and shutdown |

The initial mode is loopback under one configured SQL identity. Browser identity headers cannot select that identity. Separate query connections own their resources and use live catalog observations; a cursor is not a database snapshot. Read-only catalog access may create connection-local temporary tables; it must not modify SSISDB system objects or data.

## Data and legacy boundary

Keep the legacy adapter alongside the new API until replacement-screen parity. The API corrects mixed time cohorts, wildcard sentinels, formatted string types and unbounded reads; these corrections do not silently change the legacy parity baseline. Preserve actual NULL timings and unknown numeric codes. Child invocations are observations, and estimates remain separate from actual timing. [API semantics](API_CONTRACT.md) owns the detailed rules; [the operation matrix](API_ACCEPTANCE.md#operation-matrix) checks them.

## SQL and resource decisions

Ordinary execution sorts must seek/select the bounded page before metadata, logging and event enrichment. Global calculated sorts may calculate keys over the whole cohort; prefer narrow working rows where measurement supports it. Keep event aggregation isolated from unrelated joins. A bounded result does not bound source scans, repeated-key windows, permission checks or history-source growth.

Current measured choices—narrow calculated cohorts, cached ID selection/logging and constrained event join order—are recorded with their tradeoffs in [the SQL remedy results](API_ACCEPTANCE.md#c82b3-execution-query-remedies).

Validate source and temporary scans, actual rows, logical/LOB reads, materializations, spills, compilation, response size and elapsed time under representative identities. Retain verified reductions in work despite noisy small-catalog latency unless they cause a material regression or disproportionate complexity. Apply RECOMPILE only to query shapes with measured justification. Do not modify system indexes, use internal-table permission shortcuts, introduce NOLOCK or hide unmeasured work behind a result cache. [The workload protocol](API_ACCEPTANCE.md#workload-protocol) defines comparable measurements.

Preserve parameter binding, exact 100-ns timestamps, BIGINT strings and explicit serializers. Typed calls use the connection-local datetimeoffset converter; bind `sql_timestamp()` strings with `CONVERT(datetimeoffset(7), ?)` to preserve the seventh digit. Opt into explicit NULL binding with `declared_parameters=True` only when SQL declares every input type; retain legacy defaults for legacy queries. Each query closes cursor and connection, attempts both closes after failure, and records safe metadata after cleanup. Browser cancellation does not guarantee native SQL cancellation; driver timeouts and request/resource tests remain necessary.

## Frontend and dependency policy

Use vanilla ES modules, native DOM/events/fetch/EventSource, semantic HTML and authored CSS. **Vite is allowed** for development/HMR and production builds. **Chart/table libraries are allowed when their complexity is justified**: compare required interactions, accessibility, maintenance, bundle size, licensing and update/teardown behavior. Pin tools, keep lockfiles, bundle libraries locally and deploy prebuilt assets; server users should not need npm. Production makes no public requests for fonts, scripts or analytics.

Keep frontend pages simple and functional. Use concise labels and useful status messages; omit slogans, marketing taglines and decorative filler copy.

The native UI uses the revised neutral-grey/indigo design system. `web/src/styles.css` owns shared `--sd-*` palette and radius tokens: page `#f3f4f6`, surface `#fcfcfd`, text `#252d3a`, secondary `#566174`, border `#d6dbe3` and action `#3c56a6`. Use a 15 px base at default browser settings, system fonts, 4 px spacing increments, flat panels, 36 px controls and stronger package names/counts. Status badges retain text and use known numeric codes for restrained colour; unknown codes remain neutral. The shell supplies the page/section hierarchy, connected summary cards, table toolbar and footer. Narrow layouts stack filters and keep horizontal scrolling within the execution table. Keep this authored CSS shared by future native screens; no animation, theme switch or styling dependency is needed.

D1a uses a JS entry and Vite manifest with a relative asset base. Only `dashboard/static/app/` is generated/emptied; that output is ignored by Git and included in the prepared application delivery after building from the tracked `web/` source and lockfile. Development uses a loopback Vite harness and a same-origin `/api/v1` proxy to local Flask. The D1b Flask shell consumes the manifest through Flask's prefix-aware static endpoint, including CSS from shared imports and optional module preloads. Shell requests read build files without SQL; absent/invalid builds return a safe 503 without preventing legacy/API/health startup. The manifest is reread for each shell request so a repaired build takes effect without recreating the app. Bootstrap JSON contains only application/API/execution URL bases; D2a loads metadata separately and D2c owns execution/summary requests. Build commands, supported runtimes and packaged/ignored boundaries are in [installation](installation.md#build-the-browser-assets). Node's built-in test runner and existing Flask unittests provide focused coverage without another test dependency.

The request boundary permits same-origin GETs within the supplied API base, rejects redirects and uses same-origin credentials with `no-store`. It preserves wire strings, encodes query values, checks JSON envelopes and exposes only fixed safe error messages, known problem codes and validated request IDs. Metadata supplies limits, statuses, sorts, capabilities and the display timezone; invalid or missing consumed settings stop startup without fallback configuration. One metadata owner coalesces concurrent starts, cancels after a 10-second browser deadline and offers manual Retry without an automatic loop. Disposal clears the timer, aborts transport and rejects late generations; back/forward-cache restoration creates a fresh owner. This lifetime is separate from the later overview refresh owner.

Replace jQuery with native events/fetch, Bootstrap/SmartMenus with authored layout and keyboard-accessible controls, DataTables with bounded server-backed tables, and Morris/Raphael with SVG or a justified chart library. Provide chart text/table alternatives and small authored icons. Remove legacy assets only after reference checks and parity. Target corporate Edge/Chrome; include Firefox/Safari smoke checks when used, with no IE requirement.

Keep filters, sorting, paging, scroll, focus, selected execution and chart state during refresh. Abort obsolete requests and check request generations so stale responses cannot overwrite a newer selection. Coalesce notifications, avoid overlapping fetch/poll loops, pause hidden work and resync on return. Retain useful stale data with clear retry/connection state. Render catalog text with `textContent`, format typed values with `Intl`, show the timezone, and store only display preferences locally.

### Overview state and refresh

Phase 3 has [nine implementation tasks](PROGRESS.md#phase-3--first-native-screen-preparation). Keep browser modules around operations that share state: applying a selection, requesting an overview, rendering typed values and owning refresh lifetime. One coordinator owns the applied selection, effective creation bounds, page-entry cursor path and request generation; rendering and transport helpers do not maintain competing copies. `refresh-loop.js` owns timer scheduling and observes coordinator cycles without owning data requests or catalog state. A framework, general state library or domain class hierarchy is unnecessary for this screen.

Separate draft filter inputs, applied selection and display preferences. Shareable `/app/` URLs contain validated selection/sort/limit; opaque cursors and catalog rows stay out of URLs and persistent storage. Back/forward restores the selection and an available valid in-memory page context; a fresh load starts on page one. Navigation choices load bounded pages on demand. “All folders/projects/statuses” omits the corresponding API parameter, so a literal name such as `all` remains selectable. The selection session owns canonical names restored from URLs or chosen from options; single-line inputs are display/edit projections because they strip CR/LF. Only explicit name edits replace these values, and project browsing reads the session's exact folder.

D2b implements the filter/history boundary with exact-name inputs and native current-page choice lists. Folder changes clear the old project; project browsing requires a folder, while a manually typed project filter can span all folders. Navigation retains the current rows and page-entry cursor path, uses the advertised default limit and name/ascending order, and fetches only on initial folder loading, confirmed folder selection, explicit paging or retry. Its 15-second browser deadline, abort/generation checks and disposal prevent obsolete choices from replacing the current scope. Invalid cursors require manual retry from page one. Native status checkboxes support sets; All statuses omits the filter, including future unknown codes. Custom bound validation uses exact integer ticks and preserves supplied offsets/fractions. Invalid URLs expose Reset without an applied fallback and clear the overview.

On each new cohort, use one execution response to establish exact `meta.from`/`to`, then request summary cards with those bounds. Summary remains all-status and is not a filtered-list total. An overview generation prevents stale responses from another selection from being displayed as current; separate API requests still observe live catalog state and do not form an atomic snapshot. Keep BIGINT IDs, wire timestamps and cursors unchanged; `Intl`/browser date conversion is for display only. Custom time inputs must resolve to explicit offsets rather than silently using the browser's timezone.

D2c implements the request and rendering owner. It validates consumed row types, bounds/order, unique identities and summary status groups/totals without another schema library. A selection change clears prior rows/cards, aborts the old request and rejects late generations. Each list/summary request has a 30-second browser deadline. Execution failure prevents a summary request; transient summary failure retains current rows and retries only that summary with the same exact bounds. Denied access clears both resources. Invalid selection/disposal clears the view, and identical concurrent applies coalesce. Rendering uses native text/time/link elements, distinguishes NULL/zero/unknown values and labels elapsed time separately from actual duration. The header groups title, load state, timezone and Legacy link into one desktop row with narrow-screen wrapping.

D2d extends that owner with metadata-advertised sorts, ascending/descending direction and integer page sizes from 1 to the advertised maximum. Table changes apply to the current applied scope while preserving pending filter edits. Next/Previous fetch the server order without local sorting or cached rows. Continuations repeat the original exact effective bounds and verify unchanged cursor `as_of`/upper fence. Previous to page one retains the effective bounds but establishes a new fence, because the API supplies no first-page entry cursor; its forward path is rebuilt. Show latest and explicit Apply/order/size changes create a fresh first-page cohort. Up to eight recent selection paths remain in memory for Back/Forward; history state, URLs and persistent storage contain no cursors or rows. Ordinary reload starts fresh. Invalid/expired continuation paths reset once with a visible notice and one first-page attempt; further failure waits for user action. Empty retained pages keep Previous/Show latest. Denial clears all retained paths and displayed data. Cards are requested again with each page's exact bounds and remain live all-status observations. No total pages or snapshot guarantee is presented.

D3a implements manual Refresh through this owner. A pending refresh retains and marks existing rows/cards as previous observations. Network/deadline/HTTP transient failures retain those observations only for the same applied scope; malformed/rejected responses clear the affected stale data, and denied access clears both resources and paths. Newly returned list bounds must match before old cards can remain visible during a summary update. Resource generation times label the previous observations; idle retained counts do not claim an active refresh. Browser clocks never resolve API windows. The renderer reuses execution-ID rows and links, patches typed cells and restores the completion-time scroll position and current row focus, with the table region as fallback when a focused row disappears. Browser scroll limits still apply when document height shrinks. Name columns retain a minimum readable width inside the scrolling table. Refresh clicks coalesce while either resource is active; explicit Apply cancels a deeper refresh even for an unchanged selection. On `pagehide` all request owners are disposed. Only a browser-confirmed back/forward-cache entry retains an in-memory request-path/view-anchor checkpoint, excluding rows. Its return revalidates metadata and refetches the saved page before restoring its view. Ordinary navigation/reload starts on page one with URL selection restored. D3b adds polling and visibility recovery through the same refresh operation. D3c's available in-app browser checks pass; actual hidden-tab, cached-document and corporate-browser acceptance remain [open](PROGRESS.md#remaining-browser-acceptance).

The polling owner keeps one pending timeout, scheduled after the complete list-summary cycle. Delay is `min(300000, max(30000, ceil(cycle_ms * 5), failure_backoff_ms))`; transient-failure backoff is 30/60/120/240/300 seconds for consecutive failed cycles. Success resets the failure count. Nonretryable failure stops automatic requests pending explicit retry, selection change or pause/resume. Browser clocks only measure scheduling cost and display the next attempt; effective API bounds still come from the server. Manual work replaces the pending timer, and requests never overlap within an owner. Pause preserves manual refresh and survives selection changes. Resume refreshes immediately when idle or coalesces with active work. Hidden documents have no polling timer; an active cycle may finish while hidden or paused. Visible return requests one resync, queued after an active refresh or summary-only retry; an initial/restored/selection page load already covers return without another immediate cycle. User pause and nonretryable stopping take precedence over visibility recovery. The visibility listener, timer and requests share disposal. A browser-cache checkpoint retains pause in memory; fresh navigation/reload enables automatic updates again.

Pagination controls remain focusable when a valid selection exists, including during refresh or after the last row disappears. `aria-disabled` communicates unavailable actions; the overview owner rejects busy or unavailable paging. Completing a refresh does not move focus back after the user has moved elsewhere. Native disabling remains appropriate when no selection exists or the owner is disposed.

| Trigger | Window and page behavior |
| --- | --- |
| Apply selection, sort or page-size change | Clear cursor history and request page one. The configured default window is resolved by the server, including `AS_OF_DATE`; explicit bounds remain fixed. |
| Refresh page one manually or by polling | Retain the selected filter mode, sort and size. Re-resolve the configured default window, or reuse explicit bounds; use the returned bounds for cards. Replace the old continuation path because this request establishes a new fence. |
| Refresh a later page | Replay its entry cursor with the original exact bounds/selection. Preserve the current page context, scroll and focus. Cursor `as_of` and the upper-ID fence stay fixed; changing rows are not a snapshot. A visible “Show latest” action starts a new first-page cohort. |
| Expired/invalid cursor, including after restart | Discard the invalid path, visibly explain the reset and attempt one new first page. Further failure uses the normal error state rather than a reset/retry loop. An empty retained page offers navigation or “Show latest”. |
| Return from a hidden tab | Unless user-paused or stopped after nonretryable failure, perform one refresh using the same page/window rules, then resume the single polling schedule. Coalesce with an initial/restored/selection page load; queue one resync after an active refresh. Do not create another polling owner. |

Manual refresh, polling and visibility recovery share one request lifecycle; abort obsolete work and independently reject late generations. Preserve stale data only for a transient failure within the same authorized selection, with its last-success state visible. Clear protected data on denied access, and never label a previous selection's rows/cards as the newly selected scope. Dispose timers, listeners and pending browser requests together; backend timeouts/resource acceptance still own native SQL cleanup. Phase 5 can later reuse this refresh operation for coalesced notifications without treating phase 3 polling as streaming acceptance.

## Native execution detail and section ownership

P4.1a–P4.1c implement the detail shell, metadata/count read, shared refresh lifetime and overview integration locally, including validated selection return. Executable observations are next; the later sections below remain planned. [P4.1a–P4.7](PROGRESS.md#phase-4--native-execution-workflows) own task scope, dependencies and acceptance. The design system at `3c41da7` is a completed shared foundation. Unavailable-environment checks are parked under the user's 18 October instruction; local detail work can proceed without claiming D3 or Stage C acceptance.

**Route and startup.** The explicit Flask shell at `/app/executions/{id}` supplies prefix-aware application/API/legacy bases and a validated decimal-string execution ID. Shell rendering is database-free and shares packaged-manifest/failure behavior. The browser obtains metadata and then `/api/v1/executions/{id}`; overview date/status filters do not constrain that resource. Overview execution links now open the native route, with an explicit Legacy detail link retained on that screen. Screen dispatch is explicit, without a catch-all route or a new routing framework.

The shared metadata loader, transport and display helpers serve both screens. `mountBootstrap` owns settings/status; `overview-screen.js` owns overview-only bindings, while detail mounts its own loader/renderer. A detail screen must not require hidden copies of overview filters or extend the overview coordinator with unrelated section state. Validate each new consumed metadata/DTO field, including the separate executable-result vocabulary, when its feature is introduced. IDs, paths, cursors and timestamp strings remain exact; only display projections use browser formatting.

**Execution lifetime.** One detail owner groups the execution ID, request generation, current authorized observation, visible section states and refresh lifetime. On an ID change it cancels and clears the old view; late success, failure or denial cannot affect a newer execution. Base detail loading gates follow-up sections. Missing/hidden or denied execution clears the whole execution view and stops automatic retries. A section capability denial clears that section without inventing permission to fetch it elsewhere; an execution-scoped 404 invalidates the displayed execution. A malformed response is not stale-success evidence. Transient failure may retain labeled prior observations only within the same execution and permitted section scope, with their response times visible.

Reuse the existing refresh scheduler around the detail operation. Manual refresh, polling and visible return share one cycle; complete it before scheduling the next and coalesce repeated activation. Refresh base detail first, then only currently displayed permitted sections; do not eagerly query every tab or give each table its own polling loop. Each section identifies its query by execution ID, resource, selection/order/limit and entry cursor, and keeps its paging/focus state without caching the full collection. Switching or closing a section invalidates obsolete work. Record observed request budgets as sections are added. Dispose the screen's requests, timers and listeners together on navigation; browser cancellation still does not prove native SQL cancellation.

**Return and view state.** Generate the overview return destination from the application base and validated overview selection; never accept an arbitrary external return URL. A standalone detail deep link has a default overview destination. Preserve the current contract: actual retained browser documents may restore an in-memory page/view checkpoint after metadata and data revalidation; a fresh document restores URL selection and starts at page one. Expired paths get one explained reset. Do not persist rows, opaque cursors or protected event/value text in history state or browser storage to simulate cache acceptance. Record those two navigation modes separately in tests. Refresh patches the current view without moving focus back after a user moves elsewhere.

The detail URL's `overview` parameter contains an encoded selection query. Its link builder/parser reuse the existing validated selection fields; P4.1c generates it from the overview's applied selection, independently of draft edits. The parameter never reaches the execution API request. The explicit Overview link opens page one and says so. Only Browser Back can reuse an actual retained overview's in-memory page path. The detail's own retained checkpoint contains ID, pause and view anchors and always re-fetches its observation after settings validation. Current actual visibility/cache conditions remain NOT RUN; controlled owner/DOM cases do not close them.

**Adding sections.** Executables and child starts are observations with their own IDs, result/availability semantics and paging; they are not an inferred complete package graph. Event search, parameters and overrides obey metadata capabilities and authoritative API denials; unavailable features need a concise state, not speculative requests or automatic legacy fetching. Preserve sensitive/policy redaction, text truncation and unidentified coverage. History uses the exact identity and its own status scope, with actual timings and server estimates kept distinct. Timeline charts consume the server's calendar buckets and effective bounds. Every chart has a text/table alternative and labels its loaded scope. Share transport, formatting, CSS tokens and only repeated lifecycle behavior demonstrated by real callers; keep section-specific validation/query state behind its own boundary rather than introducing a universal domain hierarchy.

First-delivery and later-section acceptance use [the frontend procedures](FRONTEND_ACCEPTANCE.md) plus focused request/render tests. Pair observation/event/value workloads with C8.2b.2b, history/aggregate growth with C8.2b.2c, and refresh/request resources with C8.2c. These are separate measured gates even when a UI task passes locally. Keep legacy coexistence, production streaming and eventual cutover at their existing roadmap boundaries.

## Production live updates

SSE is the initial server-to-browser transport; WebSockets require a concrete bidirectional need. The transport and SSISDB change detector are separate responsibilities.

1. Use shared bounded/timed change detection per approved database/authorization scope. Detect new records **and updates to existing active executions**; a maximum execution ID alone misses transitions. Never keep an ODBC connection for the lifetime of a browser stream.
2. Own detector startup/shutdown explicitly and avoid debug-reloader duplicates. Define coordination before adding multiple workers; process-local queues do not provide cross-worker continuity, and cursors need one shared `API_CURSOR_SECRET_KEY`.
3. Send small authorized resource-change notifications, without raw messages, values or connection details. Coalesce client refetches and recheck subscription access on reconnect or identity expiry.
4. Define ordered event IDs, bounded replay and idempotent handling. Snapshot/subscription handoff must not lose changes. Unknown/expired IDs, restart, retention gaps and queue overflow require explicit resync.
5. Bound queues, subscribers, replay and message sizes. Disconnect or resync slow clients, send heartbeats, and release subscriptions on disconnect/navigation/shutdown.
6. Show connecting/live/reconnecting/paused/stale/polling state. Hidden-tab return requires resync. Fall back to data-only polling with backoff and no overlapping loops; stop polling when streaming recovers.

Validate buffering, compression, idle timeouts, heartbeats, URL prefixes and stream/API capacity on the chosen authenticated proxy and production server. A thread-per-stream server needs an explicit capacity budget. Measure database detection load and multi-tab behavior before choosing topology. Development HMR and an ordinary polling screen do not satisfy this production milestone.

## Identity and hosting

Local development binds to `127.0.0.1`. Shared hosting requires an approved audience and authenticated HTTPS proxy, no direct-access bypass, and an explicitly approved SQL read scope. A shared SQL account exposes its scope to authorized viewers; per-user rights require endpoint authorization or designed identity delegation. A browser login alone does not change SQL identity. Trust proxy headers only through the configured boundary and avoid wildcard CORS and cross-user result caches.

API events and values are disabled by default; overrides have an additional display policy. Sensitive values remain NULL in both SQL and serialization. These flags govern API routes; legacy coexistence retains its previous SQL-identity access. Host/access/startup logs need their own review in addition to safe application logs.

Hosting is deferred by the user's 15 October 2026 instruction. When resumed, select a supported server/proxy/runtime combination, certificate trust and service identity; repeat native checks under that identity. Waitress is a Windows candidate requiring stream-capacity validation. An ODBC Driver 18 migration must explicitly review encryption/certificate settings. Optional containers need a current supported OS/driver recipe; the legacy Ubuntu/Python image is not current acceptance evidence.

## Rollout and rollback

[The roadmap](roadmap.md#delivery-phases) owns delivery phases and their exit conditions. The first native screen may start after C1/C2a/C3a/C3b pass locally; this overlap does not close Stage C. Keep legacy and `/app/` side by side until parity, use an explicit default-page switch, and preserve bookmarks through route translation. Test a separate binding first. Retain the previous application and environment for rollback; no SSISDB schema migration is required. Publication follows the personal-fork-only repository workflow.

Phase 4 local work starts from the completed overview/design baseline while unavailable-environment acceptance remains explicitly open. The first native detail integration changes only the native overview's detail destination and retains a legacy link; bookmark mapping follows the section-by-section parity work. No phase 4 task retires legacy assets, changes the default homepage or resumes production hosting. The user will review the [environment-dependent browser procedures](FRONTEND_ACCEPTANCE.md); a written procedure or local simulation is not evidence that its gate passed.

## Acceptance targets

Contract and native checks cover exact-name/time/status cohorts, both global sort directions, ties/NULLs, Unicode, large IDs, precise offsets/DST, live retention and permission changes, redaction, missing observations and safe failures. Browser checks cover deep links/back-forward, keyboard/narrow layouts, literal text rendering, stale-response races and preserved state. Stream checks cover the handoff/replay/resync/cleanup cases above on the real proxy. A plain SQL Server instance without representative SSIS Catalog data is not equivalent integration evidence.

[The roadmap](roadmap.md#acceptance-budgets) owns proposed size/latency budgets. [API validation](API_ACCEPTANCE.md#workload-protocol) defines the distinct SQL, WSGI and network measurements; production stream budgets require the chosen host.

Before shared deployment, resolve audience/read scope, required SQL/ODBC/platform matrix, authentication/certificates, proxy/server capacity and any local legacy customizations. Preserve Apache-2.0 and dependency attribution.
